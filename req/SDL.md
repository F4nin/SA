# Конспект: SDL-контракт GraphQL

## Вопрос 1. Почему схему называют «центральным контрактом» и что значит «нет схемы — нет API»?

**Ответ.** Схема GraphQL — это центральный контракт между клиентом и сервером, который определяет типы данных, операции, поля и аргументы. [source:rq0d3blsdg6wbljnwk56]

- «Нет схемы — нет API» означает: без схемы нет валидного контракта, по которому клиент знает возможности сервера, а сервер знает, что исполнять.
- Каждый запрос и ответ **валидируются по схеме**: необъявленные поля и опечатки сервер отклоняет. [source:mksgdefs45m3ibbn9gh1]

Функции схемы:

1. **Валидация** запросов и ответов;
2. **Типизация** (типобезопасность на клиенте и сервере);
3. **Документирование** (схема — живая документация);
4. **Контроль доступа**;
5. **Упрощение разработки** (единый контракт для команд). [source:rq0d3blsdg6wbljnwk56]

## Вопрос 2. Разница между Query, Mutation и Subscription. Как исполняются и какие кэшируются?

**Ответ.**

| Операция | Назначение | Исполнение | Кэширование |
|---|---|---|---|
| `Query` | чтение данных | **параллельно** | **да** |
| `Mutation` | изменение данных | **последовательно** | нет |
| `Subscription` | real-time-события | асинхронно, через **WebSocket** | нет [source:t8w0ssdgq55z5fn4nh3e][source:rq0d3blsdg6wbljnwk56] |

- `Query` не меняет данные → может кэшироваться.
- `Mutation` выполняется последовательно, чтобы изменения шли в корректном порядке.
- `Subscription` — push-модель: сервер сам рассылает обновления подписанным клиентам без периодических повторных запросов. [source:mksgdefs45m3ibbn9gh1]

## Вопрос 3. Семантика `[Type!]!`, `Type!` и `Type`. Примеры nullability.

**Ответ.**

- `Type` — поле опционально (может быть `null`).
- `Type!` — поле обязательно (non-null).
- `[Type]` — опциональный список, элементы тоже опциональны.
- `[Type!]!` — обязательный список из обязательных элементов. [source:rq0d3blsdg6wbljnwk56][source:47qfqd9c4djnlg40i4dd]

Пустой массив `[]` допустим всегда — даже для `[Type!]!`.

**Nullability кодирует бизнес-правило:**

- Финансовый кейс: `closePrice` опциональна, потому что свеча за выбранный таймфрейм может быть ещё не закрыта в момент запроса. [source:o1idiwby0nkoswhuklgn]
- Кейс с товаром: `updatedAt` опционален, потому что товар мог никогда не обновляться; `createdAt` обязателен, потому что сервер всегда ставит его при создании. [source:v2x9z4rwb830hxam03jj]

## Вопрос 4. Зачем кастомные скаляры вроде `ISO8601DateTime` или `Date`? Чем лучше `String`?

**Ответ.** Кастомные скаляры задают:

- **собственный формат** значения;
- **сериализацию** (как передавать по сети);
- **валидацию** (где отсекать неверный ввод). [source:rq0d3blsdg6wbljnwk56]

`String` — это «какая-то строка», без семантики и валидации. Кастомный скаляр:

- делает схему **самодокументируемой** (понятно, что это дата);
- **валидирует** ввод (отклонит неверный формат);
- **сериализует единообразно** (все клиенты получают ISO 8601). [source:v2x9z4rwb830hxam03jj]

## Вопрос 5. Interface vs Union. Почему `... on Type` обязателен для Union?

**Ответ.**

| Критерий | `Interface` | `Union` |
|---|---|---|
| Общие поля | **Есть обязательно** | **Не обязательны** |
| Связь типов | `implements Interface` | просто перечислены |
| Когда | похожие объекты с общими полями | разные объекты без общих полей [source:rq0d3blsdg6wbljnwk56] |

- `Interface` — выносит общие поля; типы обязаны их реализовать и могут добавлять свои.
- `Union` — объединяет типы без существенных общих полей.

**Почему `... on Type` обязателен для Union:** у членов Union нет гарантированных общих полей, поэтому клиент обязан явно указать фрагмент для каждого типа, даже если имена полей случайно совпали. [source:rq0d3blsdg6wbljnwk56]

## Вопрос 6. Что можно класть в `Input`? Почему мутация часто принимает один `Input`?

**Ответ.** Внутри `Input` допустимы **только**:

- скаляры (`Int`, `Float`, `String`, `Boolean`, `ID`, кастомные);
- `Enum`;
- другие `Input`. [source:rq0d3blsdg6wbljnwk56]

**Запрещены** `Object` (`type`), `Interface`, `Union` — то есть все выходные типы.

**Зачем один `Input` вместо многих аргументов:**

1. **Удобство расширения** — добавив поле внутрь `Input`, не ломаем сигнатуру мутации и старые клиенты.
2. **Читаемость** — сигнатура не раздувается.
3. **Переиспользование** — тот же `Input` можно применять в разных мутациях.
4. **Единая точка документирования.** [source:rq0d3blsdg6wbljnwk56]

## Вопрос 7. Простые массивы vs Connection/Edge.

**Ответ.**

- **Простой массив** — для небольших стабильных списков; нет пагинации и метаданных.
- **Connection** (паттерн Relay) — для больших списков, даёт масштабируемую пагинацию. [source:rq0d3blsdg6wbljnwk56]

Поля Connection:

- `edges` → (`node` — объект, `cursor` — позиция);
- `pageInfo` (`hasNextPage`, `hasPreviousPage`, `startCursor`, `endCursor`);
- `totalCount`. [source:rq0d3blsdg6wbljnwk56]

Формула: `Connection` → `edges` → `Edge` → (`node` + `cursor`) + `pageInfo` + `totalCount`.

Минус Connection: для каждого объекта нужны `XxxEdge` и `XxxConnection` — схема разрастается. Применяем только для больших списков.

## Вопрос 8. Директивы `@include` / `@skip` и кастомные директивы.

**Ответ.** Директивы — это **аннотации/декораторы**: добавляют метаданные или управляют выполнением, не меняя форму запроса. [source:j1q70cqweq47ifoximom]

**Встроенные запросные:**

| Директива | Поведение |
|---|---|
| `@include(if: true)` | включить поле |
| `@include(if: false)` | исключить поле |
| `@skip(if: true)` | исключить поле |
| `@skip(if: false)` | включить поле [source:j1q70cqweq47ifoximom] |

**Схемные встроенные:**

- `@deprecated(reason: String)` — помечает устаревшее;
- `@specifiedBy(url: String!)` — документирует кастомный скаляр. [source:rq0d3blsdg6wbljnwk56]

**Кастомные** требуют реализации на сервере:

- `@auth(role: String!)` — авторизация/RBAC;
- `@cacheControl(maxAge: N)` — кэширование;
- `@upperCase` — трансформация результата. [source:j1q70cqweq47ifoximom][source:1rsauwt1y4lzeivrhxiv]

## Вопрос 9. Зачем `idempotenceKey`?

**Ответ.** `idempotenceKey` — это **«ловитель дублей» для операций создания**. [source:v2x9z4rwb830hxam03jj]

Проблема: при сетевом сбое/таймауте клиент повторяет запрос, и сервер может создать дубликат. Ключ позволяет серверу **идентифицировать повторную операцию** и вернуть результат первой, а не создавать новую сущность. [source:cbhqwicg4sd94sqtf1de]

Это **не** про авторизацию и не про защиту от изменения чужих объектов.

## Вопрос 10. Почему GraphQL отвечает HTTP 200 даже при ошибках?

**Ответ.** GraphQL — **RPC-стиль**: все запросы идут через POST на единый endpoint. [source:t8w0ssdgq55z5fn4nh3e]

- HTTP-статус всегда **200 OK**, даже при ошибках.
- Ошибка определяется **наличием объекта `errors`** в теле JSON-ответа, а не HTTP-статусом. [source:t8w0ssdgq55z5fn4nh3e]

Отличие от REST: в REST ошибка кодируется HTTP-статусом (404, 500), а в GraphQL — объектом `errors`.

Дополнительные статусы (400, 404, 503) — это расширение, не стандарт. [source:t8w0ssdgq55z5fn4nh3e]

## Вопрос 11. Почему GraphQL проектируют «как граф»?

**Ответ.** GraphQL — это язык обхода связанных данных: клиент в одном запросе проходит от сущности к связанным сущностям. Проектирование «как REST» (плоские изолированные запросы без связей) убивает гибкость, переиспользование и типобезопасность. [source:rq0d3blsdg6wbljnwk56]

Графовая модель:

- **корневые вершины** — `Query`, `Mutation`, `Subscription`;
- **вершины** — объектные типы;
- **рёбра** — поля (связывают тип с типом или скаляром);
- **листья** — скаляры. [source:rq0d3blsdg6wbljnwk56]

## Вопрос 12. Что такое интроспекция и почему её отключают в проде?

**Ответ.** Интроспекция — способность клиента **выгрузить полную схему** (типы, поля, операции). [source:rq0d3blsdg6wbljnwk56]

Благодаря ей работают GraphiQL/Apollo Studio, codegen, валидация. [source:1rsauwt1y4lzeivrhxiv]

В продакшене её часто отключают, потому что:

1. раскрывает структуру API злоумышленникам;
2. увеличивает поверхность атаки;
3. может косвенно раскрывать внутреннюю модель данных. [source:rq0d3blsdg6wbljnwk56]

# Переход к практике

Теперь приступаем к практической работе. Напоминаю первую задачу:

## Практическая задача №1: Сервис финансовых графиков

**Постановка:**

Банк создаёт приложение для получения цен, данных графиков и индикаторов по финансовым инструментам: акциям, фьючерсам, облигациям.

**Три операции:**

1. Получение цены по тикеру на определённый момент времени.
2. Получение данных для графика по тикеру и таймфрейму за период.
3. Подписка на обновление графика в реальном времени.

**Бизнес-правила:**

- Нет даты → самая последняя цена.
- Нет периода → данные за последний месяц.
- Графики: линейный (по ценам закрытия) и свечной (open/close/max/min).
- Точка `ChartData`: временная метка (ISO 8601), тикер, последняя цена, цена открытия, **опциональная** цена закрытия, максимальная цена, минимальная цена, **опциональный** массив индикаторов.
- Цена закрытия опциональна — свеча может быть не закрыта на момент запроса.
- Индикаторы: базовые и кастомные; `Indicator` = `id`, `title`, массив `Value`.
- Индикаторы неоднородны: в `Value` может приходить одно значение или массив значений.
- Временные метки — ISO 8601. [source:hbpavphv13ze1nuydwh3][source:o1idiwby0nkoswhuklgn]
