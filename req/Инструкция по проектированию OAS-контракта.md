## Инструкция: с чего начинать проектирование OAS-контракта

Ты верно заметил: если начинать с «напишу все базовые схемы», это сбивает. Контракт строится **сверху вниз от бизнеса, а не снизу вверх от схем**. Вот порядок, который я рекомендую как системный аналитик.

---

### Шаг 0. Начни не с YAML, а с анализа ТЗ

Это главный приём из практики курса [source:t8vns4e2qhj38r8221v4]:

1. Прочитай техническое задание **целиком**.
2. Выдели **сущности** и их атрибуты.
3. Выдели **роли** и их права.
4. Для каждой сущности определи **операции**, доступные каждой роли.

Пока не пиши ни одного поля схемы. Сначала составь таблицу:

| Роль | Действия |
| --- | --- |
| Клиент | просмотр списка, просмотр одного |
| Админ | создание, изменение, удаление |

Только после этого переходи к структуре API.

---

### Шаг 1. Определи ресурсы и HTTP-методы

Ресурсы — это **существительные во множественном числе**, а не действия [source:1s5r4vz4tbmt6a0pnxnr]:

- коллекция: `/matches`, `/orders`;
- единичный ресурс: `/matches/{matchId}`, `/orders/{orderId}`.

Коллекция и элемент — это **разные REST-ресурсы** с разным набором операций [source:ygmgyjncoevwts67ikmx].

Для каждой операции сразу определи:

- HTTP-метод;
- что приходит (query, path, тело);
- что возвращается (статус и модель).

Примерная таблица:

| Ресурс | Метод | Роль | Статус успеха |
| --- | --- | --- | --- |
| `/matches` | GET | Клиент, Админ | 200 |
| `/matches` | POST | Админ | 201 |
| `/matches/{matchId}` | GET | Клиент, Админ | 200 |
| `/matches/{matchId}` | PUT | Админ | 200 |
| `/matches/{matchId}` | DELETE | Админ | 200/204 |

---

### Шаг 2. Продумай статус-коды для каждой операции

Не оставляй все ответы «на потом». Сразу зафиксируй:

- **Успех**: `200` для чтения/обновления/удаления, `201` для создания.
- **Ошибки клиента**: `400` — невалидный запрос, `401` — нет авторизации, `404` — конкретный ресурс не найден, `409` — конфликт состояния или дубликат.
- **Ошибки сервера**: `500`.

Важные правила:

- Пустая коллекция — это `200` и пустой массив, **не** `404`. `404` уместен только для конкретного ресурса `/matches/{matchId}` [source:ygmgyjncoevwts67ikmx].
- Для удаления можно выбрать `200` с телом или `204 No Content` без тела [source:ygmgyjncoevwts67ikmx].
- Если есть идемпотентное создание, нужен `409 Conflict` с исходным ресурсом [source:1s5r4vz4tbmt6a0pnxnr].

---

### Шаг 3. Только теперь проектируй модели данных — по одной сущности

Ключевой совет: **не пиши все схемы сразу и не начинай с base-схем**. Пиши схемы по мере необходимости, начиная с **ответных моделей**, потому что они описывают, что видит клиент.

Для каждой сущности:

1. Выпиши **все атрибуты**, которые есть у ресурса в бизнес-смысле.
2. Отметь, какие обязательные, какие нет.
3. Реши, что сервер присваивает сам (`id`, `createdAt`, `status`), а что приходит от клиента.
4. Раздели **модель запроса** и **модель ответа** [source:0r2qy6hdn6dm0y7vl1tj]:

   - модель ответа содержит `id`, созданные поля, полные связанные объекты;
   - модель запроса содержит только то, что клиент может передать: без `id`, без `readOnly` полей.

Например: `Order` (ответ) и `CreateOrder` (запрос) — разные схемы, потому что при создании `id` присваивает сервер, статус по умолчанию `created`, а не передаётся клиентом.

**Base-схемы добавляй в самом конце**, если видишь реальное дублирование полей между несколькими схемами. Не создавай их заранее «на всякий случай» — это усложняет контракт без пользы.

---

### Шаг 4. Определи формат списков и пагинации

Если операция возвращает коллекцию:

- оберни список в объект, например `MatchList`, с полями `items`, `total`, `limit`, `offset` [source:1s5r4vz4tbmt6a0pnxnr];
- для пагинации используй query-параметры `limit` и `offset` с `minimum`, `maximum`, `default` [source:ygmgyjncoevwts67ikmx].

Это предотвращает «вернуть миллион записей» и позволяет аддитивно добавлять метаданные.

---

### Шаг 5. Продумай безопасность

- Определи способ аутентификации: apiKey, OAuth2, HTTP Basic [source:k3c4pqfiof1e8cdpayke].
- Если нужны роли — используй **OAuth2 со scopes**, потому что роли видны в контракте и Swagger UI.
- Для каждой операции укажи, какие scopes требуются.
- Не забудь `401 Unauthorized` для защищённых методов [source:ygmgyjncoevwts67ikmx].
- Публичные методы отметь `security: []`.

---

### Шаг 6. Собери верхнеуровневую структуру

Теперь можно писать YAML сверху вниз:

1. `openapi: 3.0.3`
2. `info` (title, description, version, contact, license)
3. `servers` (минимум два окружения)
4. `tags`
5. `paths` (операции)
6. `components.schemas` (модели)
7. `components.responses` (переиспользуемые ответы)
8. `securitySchemes`

Не забывай: `servers` — корневой ключ, не вложенный в `info` [source:xfwqq69nxb3ug7vvwyun].

---

### Шаг 7. Проверь контракт валидаторами

В конце обязательно прогони через:

```bash
redocly lint contract.yaml
spectral lint contract.yaml --ruleset .spectral.yaml
```

Redocly проверяет структуру и `$ref`, Spectral — полноту описаний [source:5zep25o6v87qusx8oeuj]. Исправляй ошибки до передачи разработчикам.
