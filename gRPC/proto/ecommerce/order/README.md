# Order Service — gRPC-контракт на Protocol Buffers

Этот мини-проект показывает полный цикл проектирования API на gRPC:

1. Моделирование сущностей и операций.
2. Описание контракта на Protobuf (proto3) по правилу **1-1-1**.
3. Генерация кода и документации через инструмент **buf**.

## Зачем этот проект

Сервис управляет заказами интернет-магазина. Он умеет:

- создавать заказ;
- получать заказ по идентификатору;
- менять статус заказа;
- отменять заказ;
- подписываться на изменение статуса заказа.

Контракт описывает **что** делает сервис и **какие данные** передаются,
но не содержит бизнес-логики — она реализуется отдельно в коде.

## Как устроен контракт

Все исходные файлы лежат в `proto/ecommerce/order/v1/`.

Каждый `.proto`-файл содержит **ровно один** главный элемент:
сообщение, перечисление или сервис. Это правило называется **1-1-1**:
один файл → один top-level элемент → одна ответственность.
Благодаря этому файлы удобно переиспользовать и рефакторить.

### Основные типы

| Тип | Что описывает |
|---|---|
| `Order` | заказ покупателя |
| `OrderItem` | позиция заказа — снимок товара на момент оформления |
| `OrderItemInput` | позиция при создании заказа (клиент не задаёт цену) |
| `Address` | адрес доставки |
| `Money` | денежная сумма в минорных единицах с кодом валюты |
| `OrderStatus` | перечисление статусов заказа |
| `OrderStatusEvent` | событие смены статуса для подписки |

### Сервис и методы

Описание сервиса — в файле `order_service.proto`.

| Метод | Тип вызова | Назначение |
|---|---|---|
| `CreateOrder` | unary | создать заказ |
| `GetOrder` | unary | получить заказ по id |
| `UpdateOrderStatus` | unary | изменить статус |
| `CancelOrder` | unary | отменить заказ |
| `WatchOrderStatus` | server-streaming | подписаться на изменения статуса |

`WatchOrderStatus` — потоковый метод: клиент отправляет один запрос,
а сервер присылает множество событий об изменении статуса,
пока соединение не закроют.

## Ключевые решения (почему так, а не иначе)

| Решение | Причина |
|---|---|
| Деньги — целое число + код валюты | `double` не может точно хранить десятичные суммы и накапливает ошибки округления |
| Статус начинается со значения `*_UNSPECIFIED = 0` | ноль — значение по умолчанию, оно должно означать «не задано», а не реальный статус |
| Значения перечислений имеют префикс имени enum | внутри пакета значения всех enum живут в одном пространстве имён; префикс исключает конфликты |
| Необязательные поля помечены `optional` | отличает «поле не передали» от «передали пустую строку» |
| `idempotency_key` обязателен при создании | при повторном запросе с тем же ключом сервер вернёт уже созданный заказ, не создавая дубль |
| `OrderItem` хранит название и цену товара | это снимок на момент заказа: изменения каталога не портят прошлые заказы |
| `OrderItemInput` не даёт клиенту цену | цену и название берёт сервер из каталога, не доверяя клиенту |
| Удалённое поле зарезервировано в `reserved` | номер и имя нельзя переиспользовать, иначе старые данные прочитаются неверно |

## HTTP-гейтвей и OpenAPI

Чтобы сгенерировать REST-обёртку и Swagger, в `order_service.proto`
для каждого метода добавлена HTTP-аннотация `google.api.http`.

Пример:

```proto
rpc CreateOrder(CreateOrderRequest) returns (CreateOrderResponse) {
  option (google.api.http) = {
    post: "/api/v1/orders"
    body: "*"
  };
}
```
Это не меняет gRPC-контракт — gRPC-клиенты работают как раньше. Аннотации лишь дают buf понять, как показывать методы в виде HTTP-маршрутов.
